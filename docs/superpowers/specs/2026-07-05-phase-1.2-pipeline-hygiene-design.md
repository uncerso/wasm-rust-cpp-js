# Phase 1.2 pipeline-hygiene — design

**Date:** 2026-07-05
**Branch:** `feature/phase-1.2-pipeline-hygiene`
**Refines roadmap:** `emscripten-wasm-opt-universality`, `size-view-toolchain-env-coverage` (реклассифицирован в perf-view), `bench-correctness-fail-surfacing`, `hashmap-string-cpp-emplace-latent` ([→ roadmap § Phase 1.2](../../roadmap.md)).
**Predecessor:** build-hygiene (PR #12, merged 2026-07-04) — ввёл общий `optimizeWasm()` + per-invocation PATH isolation.

## Goal

Батч из четырёх мелких pipeline-/reporter-hygiene правок, закрываемых одной пачкой:
финализировать унификацию wasm-opt (A), показать собранные-но-скрытые perf-данные
shape_dispatch (B), закрыть тихий correctness-fail в раннере (C), починить латентный
dup-key баг hashmap_string cpp с ре-бенчем (D). Пункты независимы по коду; C делается
раньше D, чтобы ре-бенч D шёл под защитой нового guardrail'а.

Все числа/дельты в спеке — иллюстративные плейсхолдеры до фактического запуска;
эмпирические премиссы (size-дельты A и D, perf-дельта D) **измеряются в ходе исполнения**,
не берутся из общих соображений.

## A — emscripten wasm-opt: honor spec (убрать inline)

### Находка

build-hygiene **сознательно** исключил emscripten из универсального `optimizeWasm`
(spec 2026-07-04 § Out of scope, стр. 57: «emscripten wasm-opt — остаётся внутренним у
emcc; не добавляем явный пасс — двойная оптимизация»; § cpp/emscripten стр. 77: «без
изменений в оптимизации»). НО в 8 скриптах `benches/*/cpp/build-emscripten.sh` остался
inline `wasm-opt -Oz` на size-профиле (через `${WASM_OPT:-wasm-opt}`), который
`build-cpp.ts:39` кормит pinned-бинарём. Фактическое состояние противоречит решению спеки:

- emscripten **size**: emcc-internal binaryen -Oz + inline внешний `wasm-opt -Oz` → двойная оптимизация
- emscripten **speed**: только emcc-internal -O3

Плюс `${WASM_OPT:-wasm-opt}` fallback на ambient `wasm-opt` при пустом env — determinism-риск.

### Решение

Довести решение спеки до конца — **удалить inline-пасс**, emscripten полагается только на
emcc-internal binaryen (оба профиля). Это одновременно достигает «wasm-opt вызывается в
одном месте (`optimizeWasm`) и нигде более» — inline исчезает совсем.

### Изменения

- `benches/*/cpp/build-emscripten.sh` (×8): удалить блок `if [[ "$PROFILE" == "size" ]]; then "${WASM_OPT:-wasm-opt}" -Oz … fi` + предшествующие комментарии про него. SIZE_ATTR-блок (name-bearing `module.attr.wasm`) не трогаем — он и так без wasm-opt.
- `scripts/build-cpp.ts` `buildEmscripten`: убрать `WASM_OPT: wasmOptPath()` из env-объекта (`:39`) — больше не потребляется. `wasmOptPath` import остаётся (используется `optimizeWasm` для wasi-sdk). Обновить комментарий про emcc-binaryen.
- Проверить, что `${WASM_OPT}` не читается больше нигде в emscripten-скриптах (grep).

### Acceptance

- `pnpm build:all` (cpp) собирается; determinism-guard (`test(build): determinism guard`) зелёный.
- **Замер size-дельты** emscripten size-профиля до/после (ожидание: ~0, второй -Oz почти
  идемпотентен). Если какой-то workload регрессит нетривиально — зафиксировать число и
  эскалировать (может изменить guideline-таблицы).
- Корректность (checksums) не изменилась.

## B — perf shape_dispatch coverage: сетка хитмапов + 4 detail-таблицы

### Находка

`perf-view-model.ts:162-164` исключает shape_dispatch из общих small-multiples
(`if (SHAPE_DISPATCH_IDS.has(bench.id)) continue`), а спец-виджет 2×2 heatmap читает только
`node·rust/raw` (`:230`). Данные shape_dispatch по rust/bindgen, cpp/wasi-sdk, cpp/emscripten
и по chromium/firefox **собираются в бенче, но нигде не рисуются** (perf-результаты
подтверждены в `results/raw/*/shape_dispatch_*`).

`supported` shape_dispatch **не одинаков** по 4 вариантам (проверены все spec.json, не один):
`homo_dyn` / `mixed_dyn` / `mixed_static` = js/idiomatic + rust{raw,bindgen} + cpp{emscripten,wasi-sdk};
`homo_static` = **без js** (нет `js/` каталога). Это **языковое свойство, не баг**: различие
static/dynamic dispatch — концепт статической типизации. Для cpp/rust `homo_static` vs `homo_dyn`
осмысленно; для динамического js «static» на гомогенных данных нечего выражать (типы только в
рантайме) → `homo_static·js` был бы идентичен `homo_dyn·js`, поэтому его нет. (`mixed_static·js`
существует, т.к. для *разнотипных* данных tag-switch vs полиморфный IC — реально разные стратегии.)

(Size-таб при этом полон — там toolchain-pills; env-оси нет корректно, wasm size
env-независим. Формулировка roadmap-пункта про «size-графики» ошибочна — реклассифицируем в perf.)

### Решение (согласовано через визуальный компаньон)

Заменить одиночный `node·rust/raw` 2×2 heatmap на **сетку хитмапов**:

```
shape_dispatch · warm-median (ms) · lower/darker = faster · +Δ% = dynamic vs static
                    node             chromium          firefox
                  st    dyn         st    dyn         st    dyn
  rust/raw     H  1.20  1.40 +17%   1.26  1.47 +17%   1.23  1.43 +17%
               M  1.30  1.90 +46%   1.36  1.99 +46%   1.33  1.94 +46%
  rust/bindgen H  …
  cpp/wasi-sdk H  …
  cpp/emscript H  …
  js/idiomatic H  —     1.55        —     1.62        —     1.58     ← homo·static = прочерк (см. ниже)
               M  1.60  2.10 +31%   …
```

- Строки = impl (все присутствующие в данных: rust{raw,bindgen}, cpp{emscripten,wasi-sdk},
  js/idiomatic), столбцы = env (node/chromium/firefox), каждая ячейка = мини 2×2
  (layout homo/mixed × dispatch static/dynamic), цвет по warm-median, `+Δ%` на dynamic-ячейке.
  Все impl стопкой (вариант A из мокапов — до 5×3=15 мини, оценено как «не критично много»).
- Старый одиночный 2×2 растворяется в сетке (его ячейка = rust/raw·node).
- **js-строка — обычная, из данных:** реальные значения для `homo_dyn`/`mixed_static`/`mixed_dyn`,
  а `homo_static·js` = `—` (нет данных → null → прочерк, естественно). js homo-`Δ%` не считается
  (нет static-базы), mixed-`Δ%` считается. НИКАКОГО синтетического placeholder / roadmap-задачи.
- **Пояснить прочерк**, чтобы читатель не недоумевал: короткий footnote/caption под сеткой
  («static/dynamic dispatch — свойство статической типизации; у динамического js для
  гомогенных данных `static` ≡ `dynamic`, поэтому `homo_static·js` не существует»). Это же —
  guideline-кандидат `dispatch-static-typing-property`.

Плюс **полные данные — 4 свёрнутые detail-таблицы** (вариант C2), по одной на комбо
(`homo·static` / `homo·dynamic` / `mixed·static` / `mixed·dynamic`). Каждая переиспользует
существующий рендер detail-строки (`renderDetailRow`: impl | env | init | first | warm med |
p95 | mad | cv | relSem | ok) — **без новой колонки**, тот же формат, что «details · all envs»
у остальных workload'ов. Свёрнуты по умолчанию.

### Изменения

- `packages/reporter/src/perf-view-model.ts`:
  - Обобщить построение shape-ячеек: вместо фиксированного `node|rust|raw` собирать
    `warmMedian` per (impl, env, layout, dispatch). Новая модель: `ShapeGrid` = импл-строки ×
    env-столбцы × 4 ячейки; список impl из `IMPL_ORDER`-порядка, присутствующих в данных
    (js попадёт автоматически — он есть в 3 из 4 bench-id; ячейка `homo_static·js` = null).
  - Собрать 4 detail-слайса (по комбо): переиспользовать `PerfDetailRow[]` per bench-id.
  - Union размеров/профилей в контролы (как сейчас, `:271-276`).
- `packages/reporter/src/render-perf.ts`:
  - `renderShapeSection` → рендер сетки хитмапов (impl-строки × env-столбцы), сохранить
    heat-bucket + `.dlt` Δ%; ячейки без данных (`homo_static·js`) → `—`; caption с пояснением прочерка.
  - Добавить рендер 4 detail-таблиц под сеткой (`renderPerfDetail`-стиль, обёрнутый в
    `<details>` с заголовком комбо).
  - CSS для мини-сетки (компактные ячейки).
- `docs/roadmap.md`: переформулировать `size-view-toolchain-env-coverage` → закрыт (size-таб
  полон; perf-coverage закрыт этим срезом); удалить пункт при завершении. **НЕ** заводить
  `js-shape-dispatch-impl` (js homo_static отсутствует by design — языковое свойство).
- `docs/guidelines.md` (при подтверждении): guideline `dispatch-static-typing-property`.

### Acceptance

- `pnpm build:all` reporter + `pnpm test` (view-model unit-тесты) зелёные.
- **Визуальная проверка** (iterate Phase 7): открыть отчёт, глазами — сетка мини-хитмапов +
  js-строка с реальными данными и прочерком `homo_static` + пояснение прочерка + 4 свёрнутые
  таблицы; не каша; Δ% читаемы; переключение size/profile работает.

## C — correctness-fail-surfacing

### Находка

`scripts/run-matrix.ts` `accumulateFailures` собирает только throw'нутые ошибки
(env-init `:198`, retry `:233`). Browser-loop (`:212-225`): результат, вернувшийся не-null из
`runCaseWithRetry`, пишется на диск и считается успехом (`consecutiveFailures = 0`) — **вне
зависимости от `validated:false` / `correctnessFailed:true`**. Значит тихий correctness-fail
в браузере проходит с exit 0. Node-путь (`:154` `run("tsx", …)`) бросает при non-zero exit
runner-node — **надо верифицировать**, что runner-node действительно выходит non-zero на
`validated:false`.

### Решение

- **Верификация (первый шаг):** проверить exit-код `apps/runner-node` и возвращаемое значение
  `runCaseWithRetry` на кейсе с `validated:false` (искусственно / через анализ кода
  `apps/runner-node/src/*` + harness). Зафиксировать, покрыт ли node-путь.
- **Фикс browser-loop:** после успешного возврата результата проверять
  `result.result.quality.validated === false || result.result.quality.correctnessFailed`;
  если да — записать результат (для инспекции), но добавить в `accumulateFailures`
  (→ `failures.txt` + `process.exit(1)`) и НЕ сбрасывать/учитывать как чистый успех.
- Если node-путь тоже не покрыт — привести к тому же поведению.
- Формат записи в `accumulateFailures`: `{ env, caseId, error: "correctness fail (validated:false)" }`.

### Изменения

- `scripts/run-matrix.ts`: логика проверки `quality` после `runCaseWithRetry`; при нужде node-цикл.
- Возможно `apps/runner-node/src/main.ts` / `apps/runner-web/src/worker.ts` — только если верификация покажет, что validated:false там не сигналится наверх.
- Тест: unit на функцию, решающую «is-failure» по `BenchResult.quality` (вынести чистую
  функцию `isCorrectnessFailure(result)` → тестируемо без запуска матрицы). Vitest.

### Acceptance

- `pnpm typecheck` + `pnpm test` (новый тест) зелёные.
- Синтетический `validated:false` результат → попадает в `failures.txt` + non-zero exit (проверить логикой теста).

## D — hashmap_string cpp: emplace → operator[] + ре-бенч

### Находка

`benches/hashmap_string/cpp/src/hashmap_string.cpp`: `map.emplace(k, v)` (строки **51, 107**)
резолвит dup-keys first-wins, тогда как reference (`Map.set` / `HashMap::insert`) — last-wins.
Строка 67 (`map[...] = …`) уже корректна (last-wins) — внутрифайловая несогласованность.
int-аналог починен ранее (`operator[]`), string остался латентным. (Строка 46
`pairs.emplace_back` — vector, не трогаем.)

### Решение

- `map.emplace(k, v)` → `map[k] = v;` на строках 51 и 107 (last-wins).
- Прочитать полный файл, понять 3 code-path (parse/build/lookup entries), убедиться что все
  dup-key-пути консистентны с reference.
- **Ре-бенч hashmap_string cpp** (оба toolchain'а wasi-sdk+emscripten × оба профиля speed+size).
- Замерить **checksum (корректность) + size + perf** до/после. operator[] = default-construct +
  assign vs in-place emplace — потенциально влияет на perf/size. Зафиксировать дельты; если
  значимо — кандидат в guideline / bug-report update.

### Изменения

- `benches/hashmap_string/cpp/src/hashmap_string.cpp` (строки 51, 107).
- `results/raw/` — обновлённые hashmap_string cpp результаты (ре-бенч).
- `docs/superpowers/bug-reports/2026-06-13-hashmap-int-emplace-dupkey.md` — дописать string-резолюцию.
- При значимой size/perf-дельте — `docs/guidelines.md`.

### Acceptance

- Сборка + бенч hashmap_string cpp: `validated:true` (checksum сходится) на всех 4 (toolchain×profile).
- Size/perf-дельта зафиксирована в session-state / bug-report.

## Порядок исполнения

Независимые по коду; рекомендуемый порядок волн (уточнится в плане):

1. **C** (guardrail) — раньше D, чтобы ре-бенч D ловил остаточные correctness-проблемы громко.
2. **D** (fix + ре-бенч под guardrail'ом).
3. **A** (build-скрипты + size-замер).
4. **B** (reporter — самый крупный по коду, чистый TS).

A/B/C — можно параллелить (разные подсистемы); D зависит только от C концептуально.

## Out of scope

- Реализация `homo_static·js` — **осознанно не делаем**: для динамического js static-dispatch на
  гомогенных данных ≡ dynamic (языковое свойство), был бы дубль `homo_dyn·js`. В таблице —
  пояснённый прочерк, без roadmap-задачи.
- Полный re-bench всей матрицы (schema v2 heavy re-bench — user action). D ре-бенчит **только**
  hashmap_string cpp (таргетно).
- Env-селектор / toolchain-селектор на shape-сетке (вариант A = всё стопкой, выбран).

## Риски

- **A size-регресс:** если удаление второго -Oz нетривиально растит emscripten size — ловится
  size-замером; эскалировать (guideline-таблицы). Митигация: вернуть inline через `optimizeWasm(glue.wasm,"Oz")` только для emscripten size, если регресс значим.
- **B перегруз perf-таба:** 12 мини + js-placeholder + 4 таблицы. Митигация: таблицы свёрнуты;
  визуальная проверка в Phase 7.
- **C ложные срабатывания:** если существующие results легитимно имеют validated:false по иной
  причине — уточнить семантику `quality` перед фиксом.
- **D perf/size сдвиг:** operator[] может изменить hot-path; замер обязателен, не «фикс вслепую».

## Testing / gates

Полный gate-набор: `pnpm build:all && pnpm typecheck && pnpm lint:all && pnpm test && pnpm smoke`
(build:all / smoke — вне sandbox). Новые unit: C (`isCorrectnessFailure`), B (view-model shape-grid).
Визуальная проверка отчёта (B). Determinism-guard (A).
